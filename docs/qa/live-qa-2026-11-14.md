## 1. Executive Summary

CallScope demonstrates a robust frontend architecture, responsive layouts across viewports, fast cached retrieval (< 350 ms), and functional integration with OpenServ SERV and DeepSeek Dolphin AI review pipelines. However, live proposal analysis suffers from severe reliability issues on Layer 2 networks: **Ethereum proposals achieved a 60% first-attempt success rate**, while **Base proposals achieved only 10%** (9 of 10 timed out). The primary failure mechanism is mis-anchored timestamp-to-block interpolation in `server/chain/proposal-events.ts`, compounded by public RPC rate limits on `eth_getLogs` and a lack of internal cancellation deadlines before Vercel's hard 60s lambda timeout.

**Top 5 Recommended Fixes:**
1. Fix timestamp block interpolation in `estimateBlockFromTimestamp()` to cover older proposals beyond the arbitrary 5M block boundary.
2. Implement an internal 45s `AbortSignal` deadline returning structured `analysis_incomplete` results before Vercel hits HTTP 504.
3. Add REST indexer fallbacks (Blockscout/Basescan) when RPC `eth_getLogs` returns code `-32011 request limit reached`.
4. Prompt the user for a creation transaction hash when governor log scanning fails or times out.
5. Replace synthetic fixture benchmarks and unverified "Recorded live" labels with verifiable raw execution logs.

## 4. Failure Taxonomy & Root Cause Analysis

### Class 1: Timestamp Clock-Mode Mis-Anchoring (Base L2)
- **Count**: 9 cases (B1, B3, B4, B5, B6, B7, B8, B9, B10)
- **Confidence**: 100% (Confirmed via public RPC query in `docs/qa/hypotheses.mjs`)
- **Root Cause**: In `server/chain/proposal-events.ts`, `estimateBlockFromTimestamp()` sets a lower bound of `high - 5_000_000n`. On Base (2-second block intervals), 5,000,000 blocks spans only ~115 days. For any proposal older than ~115 days (such as B1 created at timestamp `1782390843`), `targetTimestamp <= lowTs` evaluates to `true`, forcing the function to immediately return `low` (block 52,280,000). The subsequent concentric ring search covers only $\pm 24,800$ blocks (blocks 52,255,200 to 52,304,800), completely missing the actual creation block at 47,757,548.
- **Evidence**: [hypotheses.mjs](file:///c:/Users/USER/Documents/Software%20Development/AI%20SaaS/CallScope/docs/qa/hypotheses.mjs), [B1.json](file:///c:/Users/USER/Documents/Software%20Development/AI%20SaaS/CallScope/docs/qa/evidence/raw/B1.json)
- **Fix Steps & Acceptance Criteria**:
  1. Calculate target block via linear interpolation between chain genesis (or known epoch) and current block:
     $$\text{estimatedBlock} = \text{latestBlock} - \frac{\text{now} - \text{targetTimestamp}}{\text{averageBlockTime}}$$
  2. *Acceptance Criteria*: Base proposals up to 365 days old resolve within $\le 8$ seconds at $\ge 95\%$ success rate.

### Class 2: Missing Internal Pipeline Deadline (Platform 504 Timeout)
- **Count**: 10 cases (E10, B1, B3-B10)
- **Confidence**: 100% (Confirmed in `vercel.json` vs `api/_analyse.ts`)
- **Root Cause**: `vercel.json` configures `"maxDuration": 60` for `api/analyse.js`. In `api/_analyse.ts`, `executeAnalysis()` runs unbounded serial network queries without an `AbortSignal.timeout()`. When RPC queries stall or iterate through multiple fallback endpoints, the Vercel gateway kills the invocation at 60s with `504 FUNCTION_INVOCATION_TIMEOUT`, preventing the application from returning a structured `analysis_incomplete` error with diagnostic metadata.
- **Evidence**: [vercel.json](file:///c:/Users/USER/Documents/Software%20Development/AI%20SaaS/CallScope/vercel.json#L5-L8), [console-network.txt](file:///c:/Users/USER/Documents/Software%20Development/AI%20SaaS/CallScope/docs/qa/evidence/console-network.txt)
- **Fix Steps & Acceptance Criteria**:
  1. Wrap `executeAnalysis()` in an internal deadline of 45 seconds (`AbortSignal.timeout(45000)`).
  2. If the deadline fires during log scanning, catch the abort and immediately return an `analysis_incomplete` response with stage `event_lookup` and user prompt to provide the transaction hash.
  3. *Acceptance Criteria*: Zero HTTP 504 errors returned to clients; 100% of long-running queries return structured JSON within $\le 48$ seconds.

### Class 3: Public RPC Rate Limiting on `eth_getLogs`
- **Count**: 5 cases observed in RPC logs
- **Confidence**: 100% (Confirmed in `hypotheses.mjs`)
- **Root Cause**: `mainnet.base.org` strictly enforces rate limits (`code: -32011, message: 'request limit reached'`), while `base-rpc.publicnode.com` rejects block ranges older than recent history without an API token (`Archive requests require a personal token`).
- **Evidence**: [hypotheses.mjs](file:///c:/Users/USER/Documents/Software%20Development/AI%20SaaS/CallScope/docs/qa/hypotheses.mjs)
- **Fix Steps & Acceptance Criteria**:
  1. Add automatic fallback to Blockscout REST API (`/api?module=logs&action=getLogs`) or Basescan API when RPC returns `-32011` or range rejection.
  2. *Acceptance Criteria*: Graceful fallback to block explorer API with $\ge 90\%$ query success.

## 8. Evaluator Scores (1 – 20 Scale)

### 1. Technical Debt: **8 / 20**
- **Justification**: The core event retrieval subsystem (`server/chain/proposal-events.ts`) is burdened by hardcoded block depth assumptions (5M blocks) that break on Layer 2 architectures where block numbers advance rapidly, causing a 90% failure rate across real Base proposals (B1, B3–B10). Asynchronous RPC query loops are executed serially without internal timeouts, directly triggering unhandled platform gateway kills (HTTP 504) at 60 seconds. Furthermore, benchmark routines in `scripts/run-tier-benchmarks.ts` substitute hardcoded numeric constants (`8500`, `1200`) in place of empirical measurement.

### 2. Sponsor Technology Use: **11 / 20**
- **Justification**: OpenServ SERV and DeepSeek Dolphin are integrated into operational endpoints with structured JSON communication and real-time state telemetry that works cleanly on successful proposals (E3–E8, B2). However, static hand-written reviews in `server/budget.ts` are labeled as "Recorded live", misrepresenting simulated responses as live AI inferences. Additionally, the prompt injection guard shows zero delta in outputs between guarded and unguarded runs in `docs/evidence/raw/guard-2026-11-14.json`, and schema validation errors in deep review (e.g. E6) fail without fallback repair attempts.

### 3. Product Quality: **9 / 20**
- **Justification**: The application UI is well-crafted with responsive mobile/tablet layouts, fast cached retrieval (< 350 ms), and clear presentation of governance actions and calldata. However, practical usability is severely undermined by an overall first-attempt pass rate of only 35% across real proposals, subjecting users to 60-second loading freezes that terminate in cryptic gateway timeout errors. When failures occur, the interface fails to offer an immediate fallback prompt asking users for the transaction hash to rescue the analysis.

### Top 3 Changes Worth +3 Each:
1. **Clock-Mode Aware Timestamp Interpolation (+3)**: Replace the static 5M block bound in `estimateBlockFromTimestamp()` with dynamic linear timepoint estimation between genesis and chain head, ensuring Base proposals older than 115 days correctly locate their creation blocks.
2. **Internal Cancellation Deadline & Structured Partial Returns (+3)**: Implement an internal 45-second `AbortSignal` in `executeAnalysis()` that preempts Vercel's 60-second gateway timeout, returning a structured `analysis_incomplete` payload with diagnostic guidance.
3. **Indexer Fallback & Tx-Hash Recovery Prompt (+3)**: Automatically fall back to Blockscout / Basescan REST APIs when RPC `eth_getLogs` is rate-limited (`-32011`), and offer a one-click UI prompt to enter the creation transaction hash whenever event log scanning fails.
